**Stride sweep.** With p = 8, time falls from 1010.6 ms at an 8-byte gap to a
minimum of 770.9 ms at 64 bytes (1.31x faster). The largest drop is from 8 B to
16 B, and the improvement stops at 64 B, which equals the L1 cache line size.
Below 64 B, 8, 4 or 2 workers share one line, which bounces between cores on
every store (coherence invalidation). From 64 B on, each worker owns its line.
Differences at 128 B and 256 B are within the IQR and are noise. The effect is
moderate because one Python step costs about 275 ns, so the store is a small part
of each iteration.

**Scaling and Karp-Flatt.** At p = 2 and 4, speedup is slightly superlinear
(e(p) < 0). This is a baseline effect: the single worker was probably moved
between P- and E-cores by the Windows scheduler. At p = 8, e(p) rises to 0.120
for stride 1 compared with 0.062 for stride 16, so false sharing roughly doubles
the overhead. The remaining overhead at stride 16 (speedup 5.58, not 8) comes
from the hybrid CPU: work is split equally, and the 4 E-cores (about 70% of
P-core speed) finish last. At p = 12 the two strides converge (0.109 vs 0.090),
because hyper-thread siblings share one L1 cache, and SMT and E-cores limit both
cases. In both cases e(p) grows with p, so the loss comes from overhead that
increases with the number of workers, not from a fixed serial fraction.

### Analysis

**Measurement quality.** Stage A does identical work at every p in the strong
run (60,000 elements in the parent), so its time should be constant. It was
30–35 ms at p = 1 and p = 10–12, but 77–83 ms at p = 2–9, with IQRs of
283–861 ms (up to 55% of the median). A fixed workload running 2.6x slower
means the CPU itself was slowed during that part of the run, most likely by
background load or power/thermal management. The p = 2–9 strong results are
therefore unreliable (for example, p = 2 is slower than p = 1). The p = 1 and
p = 10–12 rows, and the whole weak run, have normal Stage A times and small
IQRs, so the conclusions below rely on those.

**Strong scaling vs Amdahl.** Stage A covers 5% of the elements but does only
10 operations per element against 30 in Stage B, so the measured serial
fraction is s = 0.029 and the Amdahl cap is 34.5. At p = 12 the observed
speedup is 5.74, only 63% of Amdahl's prediction of 9.10 and 16.6% of the cap.
The serial fraction is therefore not what limits this program. The loss comes
from the hardware: work is split into equal blocks, so the slowest worker sets
the time, and on the hybrid i5-12450H the slowest workers are on E-cores or on
P-cores shared by two hyper-threads. Efficiency settles near 0.48–0.50 for
p = 10–12.

**Weak scaling vs Gustafson.** Stage A is 5% of N(p), so the serial time grows
with p, from 6.4 ms to 60.9 ms (about 5 ms per extra worker). As a result,
alpha rises from 0.029 to 0.146, five times higher. Gustafson's law assumes the
serial time stays constant, and that assumption is broken here. Weak efficiency
falls to 0.537 at p = 12.

The parallel part also slows down, even though each worker always does 200,000
elements. Stage B time (total minus Stage A) is 198 ms at p = 4 (P-cores only),
235 ms at p = 5 (first E-core), 286 ms at p = 8 (all E-cores) and 356 ms at
p = 12 (hyper-thread pairs). From p = 4 to 8, 198 / 286 = 0.69, so E-cores run
at about 69% of P-core speed. This matches the 70% estimate from Phase 1.

At p = 12, Gustafson's formula gives 10.39, but the measured scaled speedup is
only 6.44 (62% of the prediction). The gap of about 3.95 is hardware overhead
(E-cores, SMT sharing, pool communication), which the formula does not model.

**Architectural inflection (p = 8 -> 9).** In the strong run, the marginal
speedup rises from +0.230 to +0.354, but these rows fall inside the disturbed
part of the run, so they cannot show the inflection. The clean weak run shows
it clearly: the marginal measured scaled speedup is +0.664 for 7 -> 8, +0.259
for 8 -> 9 (a 61% drop) and +0.011 for 9 -> 10. From p = 9 on, new workers
share a P-core with an existing worker through hyper-threading, so each one
adds very little throughput.

**Baseline note.** As in Phase 1, the single-worker baseline is relatively
slow (E_weak = 1.22 at p = 2). Windows probably schedules a lone worker less
favourably, so speedups at small p look slightly better than they are.

### Analysis

**Roofline ceilings.** The copy test moves 128 MB, ten times the 12 MB L3, so it
measures main memory: 39.93 GB/s, with a very stable IQR (0.12 ms, 4%). The
compute ceiling is only 0.3941 GFLOP/s for 8 workers, about 49 MFLOP/s per
worker, or about 41 ns per `x = x*m + c` statement. This is the cost of the
Python interpreter, not of the floating-point unit. The time is measured from
the first worker starting to the last one finishing, so the slower E-cores set
this ceiling. As a result, the ridge point is extremely low:
I* = 0.00987 FLOP/byte.

**Mapping the variants onto the Roofline.** Every variant has an intensity far
above I*: from 0.083 FLOP/byte (V2) to 10.67 FLOP/byte (V3, BS = 128). All of
them are therefore **compute-bound** and sit under the flat compute roof of
0.3941 GFLOP/s. Even for V2, the lowest-intensity variant, the memory roof is
I x BW = 0.083 x 39.93 = 3.3 GFLOP/s, 8.5 times higher than the compute roof.
Memory traffic never limits these kernels in Python.

**Why V1 is the fastest.** V1 reaches 0.0832 GFLOP/s (21.1% of the compute
roof), V2 0.0710 (18.0%) and the best V3 0.0661 (16.8%). In C, V2 and V3 would
win because they access B with unit stride and reuse tiles in cache. In Python,
the cost is set by how many interpreter operations each inner step does. V1
keeps its running sum in a local variable and does two memoryview reads per
step. V2 and V3 read and write C[i, j] on every step, which is three memoryview
accesses. One inner step costs about 192 ns in V1 and about 225 ns in V2
(per worker, 2 FLOPs each), against about 41 ns for one statement in the
compute test. A cache miss on the strided B column in V1 costs at most a few
tens of nanoseconds, so it is hidden behind the interpreter overhead.

**Tile sweep and BS*.** V3 uses the same micro-kernel as V2 plus three extra
tile loops. Small tiles add the most loop overhead: BS = 8 is 26% slower than
V2. Times level off for BS >= 32 (508–521 ms). BS* = 32 is the largest tile
that fits in the L1d of every core (24 KB, within the 32 KB of an E-core and the
48 KB of a P-core). However, the differences between BS = 32, 64, 96 and 128 are
smaller than their IQRs (21–74 ms), so this run does not show a real cache-fit
effect. The plateau comes from loop overhead being spread over longer inner
loops, not from the cache. Even at BS*, V3 is 7% slower than V2.

**Conclusion.** Cache blocking raises operational intensity (I ~ BS/12), but
this only helps when a kernel is memory-bound, meaning it sits to the left of
the ridge point. In pure Python the ridge point is about 0.01 FLOP/byte, so
every GEMM variant is compute-bound and blocking only adds loop overhead. In a
compiled language the compute ceiling would be much higher, the ridge point
would move far to the right, naive GEMM would become memory-bound, and tiles
sized to fit L1d or L2 would give large speedups.

### Analysis

**Block static.** Work per item grows as i², so contiguous block b holds a
share of ((b+1)^3 - b^3)/512 of the total: from 1/512 for worker 0 to 169/512
(33.0%) for worker 7. The measured imbalance, lambda = 2.689, matches the
theoretical 33.0% / 12.5% = 2.64. The worker times follow the same cubic
pattern: the ratio of worker 7 to worker 6 is 1.39 measured against 1.33
predicted, and worker 7 to worker 5 is 1.92 against 1.86. Workers 0-3 finish in
under 1.7 s and then sit idle while worker 7 runs for 7.0 s. Block static also
has by far the largest IQR (1231 ms, 18%). The run time depends on a single
worker, so it varies with whether that worker lands on a fast P-core or a slow
E-core.

The speedup over block static is 2.01x rather than the 2.64x the work shares
predict. When worker 7 runs alone at the end, it probably has a P-core with
full turbo and no hyper-thread neighbour, so it processes each iteration about
1.3x faster than the average worker in a fully loaded run.

**Cyclic static.** Interleaving items (w, w+8, w+16, ...) gives every worker
almost exactly 1/8 of the work. Lambda drops to 1.029 and the speedup is 1.97x.
The worker times differ by only 8% (3290-3551 ms), much less than the ~30%
P-core/E-core gap measured in Phases 1 and 2. Over a 3.5 s run, Windows
probably moved the workers between P-cores and E-cores, which averaged out the
speed differences.

**Dynamic queue and the choice of C*.**
- C = 1 gives the best time (3484.8 ms) and an almost perfect lambda = 1.001:
  all 8 workers stop within 6 ms of each other. Synchronization contention is
  negligible here because items are heavy. An average item costs about 3.5 ms
  (106.65 M iterations x ~261 ns / 8,000 items), while one lock operation on
  the shared counter costs microseconds. Even 8,000 lock operations add only a
  fraction of a percent.
- C = 8 is very close (3589.7 ms, lambda = 1.009). The difference from C = 1 is
  about the size of the IQR.
- C = 512 shows tail imbalance. There are only 16 chunks for 8 workers, and the
  last chunk (items 7680-7999) holds about 11.5% of all the work, almost a full
  fair share. The worker that takes it finishes long after the others:
  lambda = 1.522 and T_wall = 4935.5 ms, 42% slower than C = 1.
- **C = 64 is invalid.** It took 14.77 s, 4.2x longer than C = 8 and C = 512
  on either side of it. Yet its lambda is 1.043, which means all 8 workers were
  slowed down together. Its tail chunk holds only about 2.4% of the work
  (about 0.7 s at most), so in theory it should finish in about 3.5-4 s. A
  uniform 4x slowdown of every core during this ~90 s segment points to a
  system-wide disturbance (thermal or power throttling, or background load),
  like the one seen in the Phase 2 strong-scaling run. It is not a property of
  the scheduler, and it should be re-measured.

**Optimal C*.** C* = 1 is the best choice for this workload. Each item is
expensive compared with one lock operation, so the finest grain gives the best
balance at almost no synchronization cost. The general trade-off is:
- Small C gives the best balance but costs one lock operation per chunk. It
  wins when items are expensive compared with a lock.
- Large C gives few lock operations, but the last chunks on a skewed workload
  leave workers idle (tail imbalance).
- If items were cheap (microseconds each), contention would dominate at C = 1
  and the optimum would move to C = 8-64. Taking the heaviest items first
  (reversing the queue order) would also shrink the tail for larger C.

**Link to earlier phases.** Phases 1 and 2 showed that equal static splits
suffer on the hybrid i5-12450H because the slowest worker sets the run time.
The dynamic queue fixes this: faster cores simply take more chunks, so the
workers finish together whatever their speed.
